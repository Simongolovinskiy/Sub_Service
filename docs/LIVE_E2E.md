# Проверка интеграции с Remnawave

## 21 октября 2026 года

Панель: https://test-remnawave.oflvp.tech, создание аккаунта — `POST /api/users`.
Проверка выполнялась через HTTP API сервиса в отдельном Docker Compose:
PostgreSQL, Redis, миграции и четыре процесса Uvicorn. Внешние вызовы шли
в реальную панель. Её ответы отдельно сверялись с локальными результатами.

### Подтверждённые сценарии

| Сценарий | Результат |
| --- | --- |
| Readiness и liveness | `200`, ответы не кешируются |
| Регистрация и повтор email | `201`, затем `409` |
| Чтение отсутствующей подписки и повторный запрос | `404` |
| Запросы подписки неизвестного пользователя | `404` |
| Создание подписки | `201`, семь дней, совпадение ссылки и срока с панелью |
| Повтор создания с тем же ключом | Исходный результат, без нового аккаунта |
| Создание с другим ключом при существующей подписке | `409` |
| Продление и повтор с тем же ключом | `200`, ровно семь дней без повторной прибавки |
| Старый ключ создания после продления | Исходный неизменённый результат |
| Два параллельных продления с разными ключами | Общая прибавка четырнадцать дней, срок панели совпал с локальным |
| Продление отключённого аккаунта | Панель подтвердила `ACTIVE` |
| Плановое отключение | Панель `DISABLED`, локальный статус `disabled`, событие с `published_at` |
| Продление истёкшей подписки | Срок `now + 7 дней`, панель снова `ACTIVE` |

В основном сценарии создания и продлений ответов `500` не было.

Для планового отключения срок единственного E2E-пользователя в панели,
локальной подписке и актуальном событии был согласованно сокращён до 35 секунд.
Интервал scheduler на отдельном стенде составлял одну секунду. После реального
истечения срока scheduler самостоятельно отключил аккаунт; вызова worker вручную
не было. Это проверка сокращённого срока, а не ожидание семи дней.

### Найденное и исправленное расхождение контракта

Первоначально отключение не проходило: панель возвращала `400` с ошибкой
`Expiration date cannot be in the past` для PATCH с прошедшим `expireAt`.
Теперь при отключении истёкшей подписки передаются только `id` и `status`.
Проверки владельца, идентификатора, статуса и фактического срока сохранены.
Повторная проверка scheduler прошла без новых ошибок доставки.

Регрессионные проверки добавлены. Полный набор после исправления:
**151 passed**, Docker-образ пересобран.

### Оставшиеся ограничения

- `GET /api/internal-squads` возвращает `403` с предоставленным ключом.
  Аккаунт создавался с пустым списком групп; доступ к VPN-узлам не подтверждён.
- Скачивание ссылки подписки завершилось ошибкой TLS: сертификат домена
  `key.30m-keys.com`, возвращённого панелью, истёк. Проверка сертификата не отключалась.
- VPN-туннель и прохождение пользовательского трафика не проверялись.
- Отложенное ACTIVE-продление с уже истёкшим целевым сроком панель также отклоняет.
  Политика завершения такого события после длительного отказа ещё не реализована.
- Внешний API намеренно не отключался; его реальные таймауты, потеря ответа
  и отказ после записи результата проверяются локальными имитациями отдельно.

### Очистка

Созданный аккаунт отключён и удалён из панели: DELETE вернул `204`, последующий
GET — `404`. Временные контейнеры и том PostgreSQL удалены. Ранее запущенный
проект не изменялся. Токен и полная ссылка подписки в отчёт и Git не включены.

## 22 октября 2026 года — проверка после рефакторинга

Полный набор оставшихся тестов: **126 passed**. Docker-образ пересобран,
миграции применены к новой БД в отдельном Compose-стеке с PostgreSQL, Redis
и четырьмя процессами Uvicorn. API доступен на порту `18000`.
В новой БД ровно три бизнес-таблицы: `vpn_users`, `vpn_subscriptions`,
`outbox_events`; таблицы шаблонных Product и auth User отсутствуют.

Внешние вызовы выполнялись в реальную панель Remnawave. Ответы API сверялись
с локальной БД и состоянием панели. Итог основного API-прогона —
**`completed_with_http_500`**: сценарии завершены, но первоначальное создание
дважды вернуло `500`. Это не прогон без HTTP-ошибок.

### Подтверждённые сценарии

| Сценарий | Результат |
| --- | --- |
| `/healthz`, `/healthz?probe=liveness`, `/metrics` | `200` |
| Старые `/api/v1/products` и `/api/v1/health` | `404` |
| Регистрация и повтор email | `201`, затем `409` |
| Отсутствующая подписка, повтор чтения и неизвестный пользователь | `404` с ожидаемыми кодами ошибок |
| Создание подписки | Два ответа `500`, затем `201` с тем же ключом; семь дней, ссылка и срок совпали с панелью |
| Повтор создания с тем же ключом | `201`, исходный результат, без второго аккаунта |
| Создание с другим ключом при существующей подписке | `409` |
| Продление и повтор с тем же ключом | `200`, прибавка семи дней без повторной прибавки |
| Старый ключ создания после продления | `201`, исходный неизменённый результат |
| Два параллельных продления с разными ключами | Оба `200`, общая прибавка четырнадцати дней, срок панели совпал с локальным |
| Продление отключённого аккаунта | `200`, панель подтвердила `ACTIVE` и прибавку семи дней |
| Плановое отключение по истечении срока | Панель `DISABLED`, локально `disabled`, событие опубликовано |
| Продление истёкшей подписки | `200`, срок `now + 7 дней`, панель снова `ACTIVE` |

Первые два запроса создания вернули `INTEGRATION_UNAVAILABLE` через `2,010`
и `2,005` секунды при лимите операции две секунды. Следующий запрос с тем же
ключом вернул `201` за `0,542` секунды. Повтор использовал сохранённое намерение;
дублирующий аккаунт не создан. Ошибки сохранены в результате прогона.

### Проверка scheduler и истечения срока

Срок единственного тестового пользователя согласованно сокращён в панели,
локальной подписке и актуальном событии до 35 секунд. На время проверки
интервал scheduler составлял одну секунду. После реального ожидания срока
scheduler самостоятельно отключил аккаунт; worker вручную не вызывался.
Задержка от целевого срока до `published_at` составила **0,526 секунды**.
У события `attempts = 0`: ошибок доставки не было.

Первое контрольное чтение панели завершилось `ConnectTimeout`; повторное
чтение подтвердило `DISABLED`. Этот таймаут чтения не является ошибкой доставки
события. Последующее продление уже истёкшей подписки через HTTP вернуло `200`:
панель подтвердила `ACTIVE` и срок от текущего времени плюс семь дней.
Это проверка сокращённого срока, а не ожидание семи дней.

### Ограничения

Повторно подтверждены `403` на `GET /api/internal-squads` и истёкший TLS-сертификат
домена ссылки подписки `key.30m-keys.com`. Аккаунт проверялся с пустым списком
групп; проверка TLS не отключалась. Доступ к VPN-узлам, VPN-туннель
и прохождение пользовательского трафика не подтверждены.

Ранее описанное ограничение отложенного ACTIVE-продления с уже истёкшим
целевым сроком этим рефакторингом не устранялось.

### Очистка и состояние стенда

Созданный аккаунт отключён и удалён из панели: DELETE вернул `204`, последующий
GET — `404`. Локально удалены только данные этого прогона: 12 записей outbox,
одна подписка и один пользователь. Другие пользователи не изменялись.

Compose-стек оставлен работающим с API на порту `18000`. Интервал scheduler
возвращён к штатным `300` секундам; значение переменной окружения и готовность
приложения проверены после восстановления. Токен и полные ссылки подписки
в отчёт и Git не включены.

### Дополнение: выходные DTO юзкейсов

После добавления отдельных `response.py` полный набор прошёл: **127 passed**.
OpenAPI полностью совпал с прежним. Повторный прогон с реальной панелью
подтвердил регистрацию, создание, чтение, повторы и параллельные продления.
Семь запросов вернули `500 INTEGRATION_UNAVAILABLE` по двухсекундному лимиту
(один при создании, шесть при параллельных продлениях). Повторы с исходными
ключами завершили операции без дубликатов; итоговый срок панели совпал
с локальным. Результат прогона — `completed_with_http_500`.

Тестовый аккаунт удалён из панели (`204`, затем `404`), локально удалены
восемь событий, одна подписка и один пользователь. Проверку планового
отключения и VPN-трафика в этом дополнительном прогоне не повторяли.
